# Task: Build own audit/review skills from Ponytail, then audit and compare the OpenSpec and Spec Kit code

## Context

This repo (`/workspace/spec-duel`) compares two AI spec-driven development kits, OpenSpec and GitHub Spec Kit, on the same small codebase (roombook: Nx 18, NestJS 11, Next.js 15 Pages Router, React 18, TypeORM 0.3, BullMQ 5, NATS, Postgres 15, Redis 7). Read `README.md` first for the full context.

- `baseline/` is the frozen starting code (git tag `baseline-v1.1`).
- `openspec-variant/` and `speckit-variant/` each started from the baseline; each kit then built the same three changes (bookings feature, double-booking rule, page-2 bugfix) on its own.
- Both kits already pass 41/41 hidden acceptance tests. The existing report `reports/openspec-vs-spec-kit-comparison.md` covers process metrics (time, cost, tokens, documents). It does NOT deeply review the quality of the code each kit wrote. That is the gap this task fills.

## Objective

1. Study the Ponytail skills at https://github.com/DietrichGebert/ponytail/tree/main/skills and write my own versions of them in `/workspace/spec-duel/.claude/skills/`.
2. Use those skills to audit and review the code of both variants.
3. Write one comparison report with strengths, weaknesses and a final recommendation of which kit to adopt and why.

## Part 2: Audit and review both variants

### Scope

Only these folders in each variant:
- `openspec-variant/apps/`, `openspec-variant/libs/`
- `speckit-variant/apps/`, `speckit-variant/libs/`

Exclude: `node_modules/`, `dist/`, `tmp/`, `.nx/`, generated files, kit documents (`openspec/`, `specs/`, `.specify/`), and `docs/`.

### Separate kit-written code from baseline code

Most of each variant is the identical baseline. A fair comparison must focus on what each kit wrote:
- Diff each variant's `apps/` and `libs/` against the baseline (git tag `baseline-v1.1` in the variant's own git history if present, otherwise against `baseline/`).
- Review the kit-written diff in depth. Review the unchanged baseline code only where the kit's code interacts with it.
- `libs/contract` is identical in both on purpose (the API contract was fixed in the baseline). Confirm this with a diff and do not score it as kit work.

### Execution strategy: parallel audits, then one synthesis

Use this structure (best practice for independent, read-only work):

1. **Collect metrics first (main session, mechanical, no AI judgement):** for each variant, collect the numbers listed under "Code metrics" below, so both auditors get the same facts.
2. **Audit in parallel:** launch two subagents in ONE message so they run at the same time, one per variant. Both get the identical rubric and the same new audit/review skill(s) from Part 1, so the results are comparable. Each subagent:
   - works read-only (no edits to either variant);
   - must not read the other variant's code, so its findings are not influenced by it;
   - writes its findings to `/workspace/spec-duel/plans/reports/<variant>-code-audit.md`, with `file:line` evidence for every finding and a severity (critical / high / medium / low).
3. **Synthesize sequentially (main session):** after both finish, verify a sample of each auditor's high and critical findings yourself against the code (discard any that do not hold), then write the comparison report.

Include in each subagent prompt: work context `/workspace/spec-duel`, reports path `/workspace/spec-duel/plans/reports/`, plans path `/workspace/spec-duel/plans/`.

### Comparison criteria

Assess each variant against all of these:
- **Code quality:** readability, naming, consistency with the existing code, error handling, typing.
- **Code smells:** long functions, large classes, feature envy, primitive obsession, dead code, magic values, narrative comments.
- **Codebase structure:** module boundaries, layering (controller → service → repository), where logic lives, file organization and naming.
- **Duplicated code:** within a variant, and code that copies baseline code instead of reusing it.
- **Potential bugs:** race conditions (for example, overlap check vs concurrent inserts), transactions, idempotency, null/undefined handling, timezone/date handling, pagination, validation gaps, error mapping across NATS.
- **Security:** input validation, unescaped LIKE/ILIKE patterns (RULES.md R11), hardcoded config (R4).
- **Rule compliance:** RULES.md R1–R11 and the TypeScript type rules (no `interface`, no `any`, named DTOs, explicit repository return types, no `$transaction` in services, files under 200 lines).
- **Tests:** what the unit tests cover, whether they test behaviour or implementation details, missing edge cases.
- **Maintainability and extensibility:** how easy it is to understand, change and extend (for example, adding a new booking rule or a new page), coupling, and how well it follows open/closed design.
- **Frontend (`apps/web`):** component structure, state and data fetching, error and loading states.

### Code metrics ("code benchmark")

Collect for each variant, for the whole `apps/` + `libs/` scope and for the kit-written diff:
- lines of code and file count (source vs test);
- files over 200 lines;
- build, lint and unit test results (run each variant's existing scripts; report real output, do not claim passes you did not see);
- unit test count and coverage, if the existing Jest setup can produce it;
- duplication and complexity figures, ONLY with tools already installed in the repo. If a useful tool (for example `jscpd`) is not installed, ask me before installing it, and report the security details required by `.claude/rules/security.md` section 4.

Runtime performance or load benchmarking is out of scope unless I approve it.

## Part 3: Comparison report

Write `/workspace/spec-duel/reports/openspec-vs-spec-kit-code-audit.md`. Do not overwrite `reports/openspec-vs-spec-kit-comparison.md`.

Contents:
1. Summary: the verdict in a few sentences.
2. Method: scope, baseline diff, tools, the parallel-audit setup, and the skills used.
3. Metrics table: both variants side by side.
4. One section per comparison criterion: findings for each variant, with `file:line` evidence.
5. Strengths and weaknesses of each kit's code: what is good and what is bad.
6. Potential bugs list: each with severity, evidence and how to reproduce or why it fails.
7. Final recommendation: which kit should be applied and why, based on the code evidence. State how it agrees or conflicts with the process findings in `reports/openspec-vs-spec-kit-comparison.md`.
8. Limitations: for example, one run per kit, AI-based review, a small codebase.

Every statement must be backed by evidence from the code or metrics. Separate verified facts from judgement calls.
