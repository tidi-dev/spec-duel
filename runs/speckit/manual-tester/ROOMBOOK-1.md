# Test Cases: ROOMBOOK-1 - Meeting-Room Bookings

- **Jira:** none (no ticket). Source: `speckit-variant/specs/001-room-bookings/spec.md`
- **Ticket status at generation:** Draft (status of the specification)
- **Generated:** 2026-11-10
- **Scope:** Black-box manual testing of the bookings API on the gateway (create, list, read, update, delete, validation), idempotent create, the observable result of the confirmation job, and the Bookings web page at `/bookings`.
- **Out of scope:** Requirements that cannot be observed from outside the system and need a developer or code review: R11 (service ownership), R25 (re-running the processor), R33 (unchanged contract, `room` service, `/rooms` page), R34 (unit tests), R35 (build/lint/test commands), R37 (different body while the first request is still in progress), and the internal parts of R13 (single database transaction), R20/R21 (queue name, payload, job id) and R23 (worker has no database). The assumption "room filter uses the first 100 rooms" is not tested (needs more than 100 rooms). See Open Questions Q4 to Q7.

## Conventions and test data used by all cases

Every case is self-contained; this section only defines the names used inside the cases.

| Name | Meaning |
|---|---|
| `GATEWAY_URL` | Base address of the gateway for the test environment (variable name only; value given by the environment owner). API cases send requests to `GATEWAY_URL` + the path shown. |
| `WEB_URL` | Base address of the web app for the test environment (variable name only). |
| API client | The tool the tester uses to send requests and read the status, headers and body of the answer (see Q1). Every request with a body uses the header `Content-Type: application/json`. |
| `ROOM_A_ID`, `ROOM_B_ID` | Ids of two existing rooms, called "Room A" and "Room B" in the cases (see A2, Q2). |
| `UNKNOWN_ROOM_ID` | `00000000-0000-4000-8000-000000000000` (no room has this id, see A3). |
| `UNKNOWN_BOOKING_ID` | `11111111-1111-4111-8111-111111111111` (no booking has this id, see A3). |
| Fresh key | A newly generated random UUID, never used in any earlier request or test run, for example in the form `3f2b8c1e-7a4d-4e9b-9c1f-2d6a5b8e0c11`. Keys never expire, so a reused key changes the result. |
| STD body | `roomId`: `ROOM_A_ID`, `title`: `QA sync`, `organizerEmail`: `qa.user@example.com`, `startsAt`: `2026-12-01T09:00:00.000Z`, `endsAt`: `2026-12-01T10:00:00.000Z`. A case that says "STD body with X = value" changes only that field. |
| Standard booking | A booking created in the preconditions by sending `POST /api/bookings` with a fresh key and the STD body (answer 201). Its `id` in the answer is called BOOKING_ID. |
| Count for Room A | The `total` value in the answer of `GET /api/bookings?roomId=ROOM_A_ID`. |

## Assumptions

- A1: The tester has an API client that can set request headers and show the status, response headers and body of an answer, and knows `GATEWAY_URL` and `WEB_URL`. The specification does not describe how a tester reaches the system. (affects ROOMBOOK-1-TC01 to TC62, TC64, TC65, TC68, TC69, TC73, TC76 to TC78, TC80)
- A2: Two rooms exist in the test environment, called "Room A" and "Room B" here, and the tester knows their ids. The specification treats rooms as existing data and does not say how to list or create them. (affects all cases that create a booking or use the room filter)
- A3: No room has the id `00000000-0000-4000-8000-000000000000` and no booking has the id `11111111-1111-4111-8111-111111111111`. (affects ROOMBOOK-1-TC03, TC08, TC09, TC10, TC20, TC25, TC51)
- A4: Times sent as `2026-12-01T09:00:00.000Z` are returned in the same written form. The specification says "ISO 8601 UTC" without fixing the number of decimals. (affects ROOMBOOK-1-TC02, TC05, TC07, TC24, TC33, TC38, TC40, TC50, TC79)
- A5: "Nothing is stored" is checked by comparing the `total` of the room-filtered list before and after; nobody else creates or deletes bookings for the same room while a case runs. (affects ROOMBOOK-1-TC21 to TC23, TC26, TC29, TC30, TC32, TC41 to TC45, TC52, TC58)
- A6: "Keys do not expire" cannot be proven in a bounded test; a 24-hour gap is used as the practical check. (affects ROOMBOOK-1-TC53)
- A7: Simulating "no answer from the API" on the web page is done with the browser's developer tools set to Offline, and the form keeps its values after a failed submission. The specification does not say how the page behaves visually after a network error. (affects ROOMBOOK-1-TC67, TC72)
- A8: A first (non-replayed) create answer does not carry `Idempotency-Replayed: true`. The specification only says the replay carries it. (affects ROOMBOOK-1-TC49, TC58)
- A9: A deleted booking no longer counts in the list and the table. Derived from "a deleted booking MUST be gone". (affects ROOMBOOK-1-TC61, TC69, TC75)
- A10: After a successful create, edit or delete the table refreshes by itself without a page reload. The specification says the booking "appears", the row "shows the updated values" and the row "disappears". (affects ROOMBOOK-1-TC66, TC68, TC69, TC73)
- A11: The exponential backoff gives attempt 2 about 1 second and attempt 3 about 3 seconds after the first attempt, so a read about 2 seconds after creation falls before the third attempt. (affects ROOMBOOK-1-TC59)

## Open Questions

- Q1: Which API client is approved for testers, and what are the values of `GATEWAY_URL` and `WEB_URL` per environment? (affects all API cases)
- Q2: How does a tester obtain room ids and room names (a room list call, the `/rooms` page, seeded data)? Are "Room A" and "Room B" seeded? (affects all cases that create a booking or filter by room)
- Q3: Must the `Idempotency-Key` be a specific UUID version (for example version 4), or is any UUID accepted? Is an empty header value treated like a missing header? (affects ROOMBOOK-1-TC41, TC42 and every create)
- Q4: Who verifies the internal requirements a tester cannot see: service ownership and gateway without rules (R11), one database transaction (R13), queue name, payload and job id (R20, R21), worker without database (R23)? Is there a queue dashboard a tester may use to count jobs? (affects ROOMBOOK-1-TC57, TC61; R11 uncovered)
- Q5: How can a tester send two requests at the same moment, and how can a create be held "in progress" long enough to force the 409 (R16) and the 422-while-in-progress case (R37)? Without a tool or a test hook these stay unproven by manual testing. (affects ROOMBOOK-1-TC45; R37 uncovered)
- Q6: Is there a way for a tester to run the confirmation processor a second time or repeat an outcome report (R25, SC-005)? If not, who verifies it? (R25 uncovered)
- Q7: R33, R34 and R35 (unchanged contract, `room` service and `/rooms` page; unit tests; build, lint and test commands) are developer checks. Confirm they are verified outside manual testing. (R33, R34, R35 uncovered)
- Q8: What is the exact written form of times in answers (decimals of seconds)? Are a time with an offset such as `2026-12-01T16:00:00+07:00`, a date without a time, or a time without `Z` accepted or rejected as "strict ISO 8601"? (affects ROOMBOOK-1-TC02, TC07, TC32)
- Q9: What are the exact `message` texts for each error code, and may an error answer contain fields other than `statusCode`, `errorCode`, `message`? (affects ROOMBOOK-1-TC10, TC70, TC76, TC77)
- Q10: Which error code is answered when an update contains `roomId` or `organizerEmail`? The edge case only says "answered 400". Are other unknown fields in a create or update body also rejected? (affects ROOMBOOK-1-TC35, TC36)
- Q11: Does an update with an empty body change `updatedAt`? Does a title made only of spaces count as a valid 1 to 120 character title? Is the title trimmed? (affects ROOMBOOK-1-TC38, TC26)
- Q12: Which HTTP status accompanies `UNAVAILABLE.SERVICE`? Can the environment owner stop the `room` service and make the queue unreachable on request, and how long does the gateway wait before answering? (affects ROOMBOOK-1-TC58, TC62)
- Q13: How can a tester make the page's load fail with an API error answer (not a network failure), so that the error state on load can be checked? What does the page show on a network failure, where there is no API `message`? (R32 partly uncovered; affects ROOMBOOK-1-TC67, TC72)
- Q14: What are the labels and wording on the page: column headings, date and time format, form field labels, the submit button, the edit, save and delete actions, the confirmation dialog and its buttons, the filter's "all rooms" option, the paging controls, the loading indication and the empty-state text? (affects ROOMBOOK-1-TC64 to TC70, TC73 to TC75, TC78, TC80)
- Q15: Does the create or edit form validate values before sending (for example end before start, empty title, bad email)? If yes, what does it show, and which API error can a tester trigger from the form? (affects ROOMBOOK-1-TC70)
- Q16: After a create on a filtered or paged table, where does the new row appear (current page, first page, sorted by start)? Does the room filter reset? (affects ROOMBOOK-1-TC66, TC71, TC72)
- Q17: Is `total`/paging on the web page combined with the room filter (paging restarts at page 1 when the filter changes)? (affects ROOMBOOK-1-TC78)
- Q18: The assumption "room filter and room names come from the first 100 rooms" is untested. What should the page show for a booking whose room is not among those 100? (no case)
